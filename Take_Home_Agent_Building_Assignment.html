Take-home assignment 3

Build a multi-agent research assistant

In this assignment the candidate is required to build a small team of agents that answers questions about a company's internal documentation: retrieving evidence, checking claims, citing sources, and showing its work. The candidate is expected to assemble these components end to end and measure how well the resulting system performs.

Submit: Git repository link + LangSmith access Deadline: September 20, 2026 at 11 PM

1. The scenario

Kestrel Labs is a fictional company that sells Kestrel, a product-analytics and event-pipeline SaaS. Like most companies, its internal wiki has grown over time: product specs, release notes, pricing pages, engineering runbooks, incident post-mortems, HR and security policies, and customer onboarding guides. Some pages are current; some have not been touched in a while.

The task is to build a research assistant that a new Kestrel employee could use to ask questions about the company and receive answers they can trust. "Trust" means every answer is backed by the documents, points to exactly where the evidence came from, and is honest when the documents do not settle the question.

Why a fictional company? Kestrel Labs does not exist, so no language model knows anything about it. A right answer can only come from retrieving the right document. That makes it possible to distinguish a system that retrieves well from one that merely guesses well.

Reading the corpus before designing the system

Candidates should spend twenty minutes reading the corpus before designing anything. A few observations should shape the design:

  • Documents were written at different times and are not all kept in sync. When two documents disagree, the published date is usually the clue to which one is current.
  • Plenty of reasonable questions are simply not answered anywhere in the corpus. The assistant should say so rather than improvise.
  • Many good answers need more than one document: an incident post-mortem names the fix, a release note dates it, and a pricing page says which customers get it.

A scoring key covering all of these cases is held by the reviewers. It will not be shared with candidates, but the assistant should be built on the assumption that it will be asked questions of each kind.

3. What to build

3.1 A multi-agent system

  • Use at least three agents with distinct responsibilities. A planner or router, a retriever, a critic or verifier, and a synthesiser is a sensible starting point; any three or more well-justified roles are acceptable.
  • Give the agents an explicit way to pass work between them, either a hand-off protocol or shared state, so that later agents can see earlier decisions and the evidence that was retrieved.
  • Support multi-turn conversations. A follow-up such as "how many of them can I create?" must resolve against the previous turn.
  • Give at least one agent a tool: search over the corpus, citation lookup, query decomposition, or another well-justified capability.
  • Use a lightweight local vector store such as Chroma, FAISS or LanceDB.
  • Orchestration may use LangGraph, CrewAI, AutoGen, LlamaIndex, plain LangChain, or a custom loop. The design document should state which was chosen and why.

3.2 Grounded, cited answers

  • Retrieve before answering any question about Kestrel. Every final answer cites the chunk_id and title of the evidence it rests on.
  • The critic or verifier checks each material claim against the retrieved context and records a verdict: supported, partially_supported, conflicting_evidence, or insufficient_evidence.
  • When evidence is missing, the system should say so plainly. When sources disagree, it should present both, state which is more reliable, and explain why.

3.3 An evaluation suite

  • Write at least 15 original questions against the corpus. Include single-hop, multi-hop, conflicting-evidence, unsupported, and follow-up questions, and record the expected answer and the chunks that support it.
  • Measure retrieval quality, answer faithfulness, answer relevance, and end-to-end correctness. Add at least one further defensible metric: an LLM-as-judge score, citation precision, or another suitable measure.
  • Act on the evaluation results. Submissions must show one concrete change made to the system because the numbers or the traces indicated it was needed, with before-and-after results.

3.4 LangSmith observability

  • Trace the whole workflow in LangSmith so a reviewer can follow a question from router to final answer, including every retrieval and every agent's input and output.
  • Run the evaluation suite as a LangSmith dataset and log the results there. Attach feedback or custom metrics to runs.
  • Trace at least three representative runs, including one unsupported and one multi-hop question.
LangSmith sharing: Access to the LangSmith project should be granted to radialpulse@nxtwave.co.in so reviewers can inspect traces, dataset runs, and metrics.

3.5 A simple frontend

A minimal web UI (Streamlit, Gradio, a small React page, or similar) should support multi-turn questions and visibly show the answer, its citations, and the status of each agent as the run progresses. Visual polish is not required; the priority is making the system's behaviour visible.

4. Ground rules

  • Generation: use a free-tier provider, preferably Groq or Gemini. Other free tiers are acceptable if documented.
  • Embeddings: use a local embedding model (a sentence-transformers model, for example). Hosted embedding APIs are not permitted. The model should be named in the README.
  • Respecting the free tier: keep embedding and generation calls sequential, cap output lengths, and handle HTTP 429 with bounded retry and backoff.
  • The corpus is read-only. Commit corpus.jsonl unchanged at the root of the repository; its hash will be checked. Evaluation questions should be kept in a separate file.
  • One command. After setting environment variables, the whole system should run end to end with a single command or notebook.
  • No secrets in Git. Keys such as GROQ_API_KEY, GEMINI_API_KEY and LANGSMITH_API_KEY should be read from the environment, with a .env.example provided.

5. What to submit

A link to a Git repository containing:

  • The working pipeline, a README with setup and run instructions, and .env.example.
  • corpus.jsonl, unchanged, at the repository root.
  • A short design document with a one-page architecture diagram: the agents used, how they hand off, the orchestration choice, and why.
  • The evaluation script or notebook.
  • A results/ directory in the format below.
  • A brief reflection: trade-offs, cost and latency observations, what worked, and what would be done next.
  • Access to the LangSmith project (a shareable link or an invitation for the reviewer), showing traces and the dataset evaluation run.
